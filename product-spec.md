# PR-Whisperer: Product Specification
**"Speak Your Code Review. Ship Clean PRs."**

---

## 1. Executive Summary & Vision

### 1.1 The 2026 Developer Bottleneck
In 2026, generative AI coding assistants (Claude Code, Cursor, GitHub Copilot Workspace, Codex) allow software developers to generate 1,000+ line pull requests in under 30 seconds. However, the human review process has remained chained to manual keyboard input:
- Engineers spend an average of **45–90 minutes per PR** clicking through fragmented web diffs, typing repetitive comments line-by-line, formatting markdown snippets, and manually checking for OpenAPI schema drift.
- Review fatigue causes critical vulnerabilities—such as hardcoded API keys, unescaped SQL fragments, missing authentication decorators, and undocumented API route changes—to slip into production.
- Even after typing feedback, the engineer must re-summarize their findings into an AI prompt so their coding agent can fix the PR.

### 1.2 The PR-Whisperer Solution
**PR-Whisperer** transforms the code review workflow into a continuous, voice-first conversation powered by **Wispr Flow**. A reviewer holds down their Wispr Flow hotkey, speaks a natural, stream-of-consciousness critique while scrolling through the diff, and releases the key.

PR-Whisperer automatically:
1. Ingests and tokenizes the natural voice transcript via Wispr Flow.
2. Performs deterministic AST and regex security scanning (hardcoded secrets, SQL injection, missing auth dependencies).
3. Compares unified git diffs against the canonical `openapi.yaml` contract to detect undocumented endpoints or schema drift.
4. Synthesizes the spoken critique and guardrail findings into precise, file-and-line-pinned GitHub review cards (`category`, `severity`, `spoken_excerpt`, `polished_comment`, `suggested_patch`).
5. Generates a 1-click **Coding Agent Fix Pack** formatted for Claude Code, Cursor, and Antigravity, also queryable via MCP (Model Context Protocol).
6. Provides **QuerySpeak**, a voice-driven natural language audit bar to interrogate past review sessions and cross-repo audit logs.
7. Maintains carrier-grade observability via OpenTelemetry (`trace_id` correlation across spans, structured JSON logs, and Prometheus metrics) with a self-healing on-call responder agent.

## 2. Target Personas & Use Cases

### 2.1 Primary Persona: Staff / Lead Engineer ("The Overwhelmed Reviewer")
- **Profile**: Reviews 15–30 pull requests per day generated by junior developers and autonomous coding bots.
- **Pain Points**: Repetitive typing, wrist strain, context switching between diff viewers, terminal linters, and OpenAPI specifications.
- **Goal**: Rapidly dictate high-signal architectural and security feedback without lifting hands to type line comments.

### 2.2 Secondary Persona: Hackathon Judge & Open-Source Maintainer ("The Rapid Evaluator")
- **Profile**: Evaluates projects under tight time constraints (e.g., WeMakeDevs x Wispr Flow Hackathon and DataTalksClub AI Dev Tools Zoomcamp).
- **Pain Points**: Setup friction, broken API keys, complex OAuth authorization steps.
- **Goal**: One-click test pre-seeded realistic PR scenarios, test voice simulation, and verify deterministic offline fallbacks in under 2 minutes.

### US-01: Pre-Seeded & Custom PR Diff Workspace
**As a** software engineer or hackathon judge,  
**I want** instant access to 3 realistic, pre-seeded "Bad AI-Generated PRs" as well as the ability to import custom unified git diffs,  
**So that** I can immediately evaluate real-world review workflows without configuring complex GitHub OAuth tokens.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: Judge Selects Pre-Seeded PR**
  - **Given** the PR-Whisperer workspace UI is loaded in the browser,
  - **When** the user clicks on any pre-seeded scenario (`PR-101: Stripe Payment Gateway`, `PR-102: User Profile Service`, or `PR-103: Analytics Webhook`),
  - **Then** the application immediately displays the PR title, author, branch, metadata badges, and a split-pane syntax-highlighted git diff with file tree navigation.
- **Scenario 2: Custom PR Ingestion**
  - **Given** a developer has a raw unified git diff from their local repository or CI pipeline,
  - **When** they click "Import Custom PR", paste the diff text along with title, repo, and branch name, and submit the modal,
  - **Then** `POST /api/v1/prs` persists the PR record in SQLite/PostgreSQL and navigates the diff viewer to the newly created PR with zero page reload.
- **Scenario 3: Zero-Config Judge Experience**
  - **Given** the app is started in an isolated container without external GitHub credentials,
  - **When** the judge visits `http://localhost:5173`,
  - **Then** all 3 pre-seeded PRs are automatically seeded into the database via Alembic/SQLAlchemy startup hooks with ready-to-use sample transcripts.

### US-02: Wispr Flow Voice Review Analysis
**As a** code reviewer holding my Wispr Flow dictation hotkey,  
**I want** to speak a continuous, unstructured critique of the code diff,  
**So that** PR-Whisperer automatically segments my critique into professional, line-pinned review cards with suggested code patches.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: Multi-Finding Voice Dictation Processing**
  - **Given** the reviewer is viewing `PR-101` and holds their Wispr Flow hotkey to dictate:  
    *"Hey, in stripe_client.py around line 42, you have hardcoded a live secret key sk_live_abc123. Please move that to environment variables. Also in line 88, you are concatenating raw query strings into SQL which opens up SQL injection. In checkout.py line 15, this endpoint doesn't check JWT permissions."*
  - **When** the reviewer submits the transcript via the Voice Review Bar (or clicks "Simulate Wispr Flow Dictation"),
  - **Then** `POST /api/v1/prs/{pr_id}/voice-analyze` processes the transcript and returns a `VoiceReviewSession` containing:
    1. A list of `ReviewCommentItem` objects with exact `file_path`, `line_start`, `line_end`, `category` (`Security`, `Contract Drift`, `Performance`, `Bug`, `Test Gap`), and `severity` (`Critical`, `Warning`, `Suggestion`).
    2. A `spoken_excerpt` echoing the user's spoken words.
    3. A `polished_comment` written in constructive, professional GitHub review phrasing.
    4. A syntactically valid `suggested_patch` showing the replacement code.
- **Scenario 2: Visual Highlighting on Diff Viewer**
  - **Given** the review session is created,
  - **When** the frontend receives the review payload,
  - **Then** the diff viewer highlights the referenced lines with color-coded severity badges (Red: Critical, Amber: Warning, Blue: Suggestion) and auto-scrolls to the line when a review card is clicked.
- **Scenario 3: Deterministic Fallback Mode**
  - **Given** `GEMINI_API_KEY` is unset or an upstream AI quota error occurs,
  - **When** the voice transcript is submitted,
  - **Then** the backend seamlessly executes rule-based heuristic token parsing and AST analysis without returning a 500 error, guaranteeing 100% test and demo reliability.

### US-03: Deterministic Guardrails & OpenAPI Drift Scanner
**As a** team lead,  
**I want** PR-Whisperer to deterministically scan the diff for security flaws and API contract drift against `openapi.yaml`,  
**So that** human oversight is augmented with mathematical, zero-hallucination guardrails and an objective `readiness_score`.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: High-Severity Secret & SQL Injection Detection**
  - **Given** a diff containing `sk_live_[0-9a-zA-Z]{24}` or `f"SELECT * FROM users WHERE id = '{user_id}'"`,
  - **When** the guardrail scanner evaluates the diff,
  - **Then** it generates deterministic `guardrail_alerts` flagged with `rule_id: SEC-001` (Secret Detected) and `rule_id: SEC-002` (SQL Concatenation), independent of any LLM analysis.
- **Scenario 2: OpenAPI Contract Drift Detection**
  - **Given** the diff modifies or adds an endpoint in `checkout.py` (e.g. `POST /api/v1/payments/refund`) that does not exist or has altered schema properties compared to root `openapi.yaml`,
  - **When** the OpenAPI drift analyzer runs,
  - **Then** it flags `rule_id: DRIFT-001` with severity `Critical` or `Warning`, highlighting the missing path, parameter discrepancy, or undocumented response code.
- **Scenario 3: PR Readiness Score Calculation**
  - **Given** a completed review analysis,
  - **When** findings are aggregated,
  - **Then** the system computes a deterministic score (0–100) where:
    - Base score = 100
    - Each Critical issue deducts 25 points
    - Each Warning issue deducts 10 points
    - Each Suggestion deducts 3 points
    - The final score is clamped between 0 and 100 and displayed prominently in the UI.

### US-04: 1-Click Coding Agent Fix Pack & MCP Context Export
**As a** developer who just received a voice code review,  
**I want** to export a comprehensive, structured prompt and expose it via Model Context Protocol (MCP),  
**So that** my coding agent (Claude Code, Cursor, Antigravity) can immediately fix all flagged issues without manual prompt engineering.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: One-Click Fix Pack Clipboard Copy**
  - **Given** a completed review session with 3 comment items and 2 guardrail alerts,
  - **When** the user clicks "Copy Coding Agent Fix Prompt",
  - **Then** the system copies a markdown prompt formatted with:
    - PR Context (Repo, Branch, Target Files)
    - Consolidated Findings grouped by severity and file location
    - Concrete unified diffs for suggested patches
    - Clear instructions for the agent to run tests and verify OpenAPI contract conformance.
- **Scenario 2: MCP Server Integration**
  - **Given** an external coding assistant connected to `mcp-server/server.py`,
  - **When** the agent invokes tool `get_pr_fix_context(pr_id=101)`,
  - **Then** the MCP tool returns a clean JSON structure containing all active review comments, diff chunks, readiness score, and contract drift findings.

### US-05: QuerySpeak Voice Audit Bar
**As an** engineering manager or auditor,  
**I want** to speak natural language voice queries across all historical PR reviews,  
**So that** I can instantly query organizational code quality and security trends without writing complex SQL.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: Natural Language Voice Query Execution**
  - **Given** multiple PR reviews have been conducted across the repository,
  - **When** the user clicks the QuerySpeak input and dictates: *"Show all critical security issues in payment PRs"*,
  - **Then** `POST /api/v1/queryspeak` extracts the intent (`severity=Critical`, `category=Security`, `keyword=payment`), filters the relational database, and returns:
    1. A list of matching review comments and PR references.
    2. Interpreted filter badges displayed in the UI.
    3. An executive `insight_summary` (e.g., *"Found 4 critical security findings across 2 payment pull requests, primarily involving hardcoded credentials and raw SQL queries."*).
- **Scenario 2: Empty or Broad Query Handling**
  - **Given** a query that matches no records (e.g. *"Show issues with Kubernetes Helm charts"* when no such files exist),
  - **When** QuerySpeak executes,
  - **Then** it returns an empty results list with a helpful suggestions banner rather than an unhandled exception.

### US-06: Full-Stack Observability, User-Impact Alerting & On-Call Remediation
**As an** SRE or On-Call Engineer,  
**I want** all voice review transactions traced with OpenTelemetry, user-impacting errors alerted in real time, and an automated on-call responder agent to propose bounded remediation diffs,  
**So that** production errors are correlated by `trace_id` and resolved with zero secret leakage.

#### Acceptance Criteria (Given / When / Then)
- **Scenario 1: Trace ID Injection & Structured Correlation**
  - **Given** a voice analysis request is initiated,
  - **When** the FastAPI backend processes the request,
  - **Then** an OpenTelemetry span is generated with a unique `trace_id` that is injected into response headers (`X-Trace-ID`), structured JSON log outputs, and frontend state.
- **Scenario 2: Zero Leaked Secrets in Telemetry**
  - **Given** a transcript containing sensitive tokens (`sk_live_12345` or `Authorization: Bearer xyz`),
  - **When** OpenTelemetry logs and metrics are exported,
  - **Then** a deterministic secret scrubber replaces all API keys and bearer tokens with `[REDACTED_SECRET]` before writing to telemetry sinks.
- **Scenario 3: User-Impact Incident Simulation & Automated On-Call Agent**
  - **Given** a reviewer triggers an error (e.g. simulated parsing crash or rate-limit failure via `simulate_failure=true`),
  - **When** `POST /api/v1/incidents/simulate-and-respond` is called,
  - **Then** the system:
    1. Increments `voice_analyze_error_rate` counter in Prometheus metrics.
    2. Registers an active `IncidentAlertEvent` in the database.
    3. Triggers the On-Call Responder Agent (`role:oncall`), which reads the read-only incident evidence packet, identifies the root cause, generates a bounded remediation git diff, marks the incident resolved, and records an auditable post-mortem log.

## 5. Non-Goals & System Boundaries

To maintain laser focus on the evaluation rubrics and prevent scope creep:
1. **No Custom ASR Model Training**: PR-Whisperer relies exclusively on Wispr Flow (and Web Speech API / mock audio transcript fallbacks) for voice-to-text dictation. We do not train, fine-tune, or host heavy speech-to-text models like Whisper locally.
2. **No Mandatory GitHub OAuth Barrier**: Evaluators and judges can test 100% of the workflow without providing personal GitHub access tokens or authorizing OAuth applications. Diff pasting and pre-seeded PRs provide instant accessibility.
3. **No Unbounded Agent Code Execution**: The On-Call Responder Agent operates in a strictly read-only analysis mode with bounded diff generation. It does not auto-merge code to production branches without human approval.
4. **No Proprietary Third-Party Database Dependencies**: The application operates identically on local SQLite (`sqlite:///./pr_whisperer.db`) and containerized PostgreSQL (`postgresql://postgres:postgres@db:5432/pr_whisperer`).
